# One-shot host HTTPS entry relay

The one-shot MCP page gate accepts the exact entry GET only as a **main-frame document navigation**. A same-URL image/fetch request or iframe navigation is aborted before the private relay is contacted and does not consume the one allowed navigation. This is a request-scope guard, not support for subresources, login, redirects, or real application success.

An independent [static JS/CSS bundle prototype](WEB_STATIC_ASSETS.md) reuses the DNS/TLS boundary and has its own private relay and pinned-MCP direct test. It is **not connected** to this `ExactEntryRelay`, managed scheduler or task worker. This one-shot entry remains HTML-only and no-script until a separately approved managed browser-asset task is implemented and tested.

`aos.web_https_relay.ExactEntryRelay` is an experimental **host-side transport primitive**, not a web-task runner. It accepts one stored staging/production profile and a canonical `WebTaskAdmissionDraft` only after exact profile and binding SHA-256 confirmations. It reopens the immutable profile chain, requires `browser.navigate` in the task draft, and binds a Unix socket inside one owner-only directory below ignored `data/`. A client may request only `GET` of the profile's exact HTTPS entry URL with the same binding hash **and a fresh 256-bit client token**. The token is generated when the relay is constructed; the scheduled path constructs it only after manual approval. Invalid requests receive a generic denial; eight attempts or the finite accept window end the service. At most one accepted request is fetched, with no automatic retry after uncertainty.

The host fetch reuses the explicit preflight's public-IP DNS check, selected-IP connection, TLS hostname verification, non-redirected `200 text/html` rule and 65,536-byte body limit. It sends fixed request headers and **no cookies, Authorization header, client-supplied headers or POST body**. The body crosses the private socket as bounded base64 for a browser route to fulfill; it is not written to source, a trajectory or the relay report. The report contains hashes/counts only and keeps browser identity, execution, collection and training authority false. Socket cleanup checks the original inode rather than deleting a replacement.

The opt-in integration tests start a separate owned Ubuntu/X11/Chromium Docker desktop still configured with `--network none`. One test uses direct Playwright; another launches the **pinned Playwright MCP CLI** with an `--init-page` route generated by `remote_entry_page_gate_source`. That route allows only one exact GET, verifies the relayed body hash, fulfills it with a no-script/no-form CSP, and aborts an off-entry navigation. `DesktopRemoteEntryMCPRuntime` also binds this route to a separate owned, pinned MCP worker. After allocating its runtime ID, `runtime_pin()` produces the exact live browser/desktop/image/MCP/worker pin; the caller binds the task draft to that pin, confirms both hashes, constructs `ExactEntryRelay`, then calls `attach_relay()`. A mismatched draft pin is rejected before socket binding, and the pin is rechecked at start. The worker permits only one `browser.remote.open` and bounded read-only `browser.remote.observe`, denying arbitrary MCP tools. The host side uses a **temporary loopback TLS server**, a synthetic certificate and a patched public DNS answer. The visible Chromium receives one synthetic HTML page while no remote domain is contacted. This proves isolated MCP transport, not a user-provided website, account, login or dynamic application.

An additional opt-in end-to-end UI test uses the real authenticated FastAPI console, built React UI in a separate host Playwright browser, pinned real Decider and the owned Ubuntu MCP desktop. It does not mock `/api/tasks`: EN/TR task selection, disabled approve-all/learning controls, pending manual approval before any GET, one approved `/entry` GET, succeeded job, one real S1 model call and independent verification are checked together. The test still intercepts the synthetic `.invalid` hostname to a temporary local TLS server; it does not exercise a user-provided website or the managed 8765 session.

For a **new** managed real-model session, `./scripts/aos-v1 start --remote-entry-profile-sha256 <registered-profile-sha256> --remote-entry-task-file data/<private-task>.json` also exposes this one-shot kind. Before stopping an existing session, the same pair can be checked with `./scripts/aos-v1 preview-remote-entry --remote-entry-profile-sha256 <registered-profile-sha256> --remote-entry-task-file data/<private-task>.json`; preview reports the canonical task digest without opening a port, starting a session, fetching a site or granting execution. The input must be an owner-only 0600 canonical web task under ignored `data/`, bound to an existing staging/production profile; the fixed pinned MCP bundle is used. The manager checks the profile/task before launch, copies the canonical task to its private session directory, records only profile/task SHA-256 pins in state, and passes a second task-file digest check to the backend. Missing, wrong, symlinked, public or fixture-mode inputs fail closed. The current managed session is never hot-upgraded; a controlled stop and a new start are required. This does not grant account access, arbitrary navigation, collection or learning on remote content.

The separately opt-in `browser_remote_entry` scheduler kind binds a canonical task and registered profile to that live runtime, saves an append-only job/run/profile/draft record in migration `0012`, and checks the binding again at gateway boundaries. It obtains a fresh manual `browser.remote.open` approval **before** creating the relay socket or starting the MCP worker. The authenticated console exposes the task through `/api/tasks` and accepts its approval through `/api/approvals/{approval_id}`; owned synthetic-TLS API tests with a labelled fixture and separately the pinned real Decider check auth, advertised scope, approve-all/learning rejection, a bad approval hash, zero pre-approval GETs, one approved GET and the persisted verification. The token passes to the pinned worker over its private stdin, **not** argv, status, trajectory or the relay report. The worker embeds it in a mode-0600 temporary MCP page gate and removes that directory at exit. `browser.remote.observe` is read-only and records only URL plus title/first-heading SHA-256 fingerprints. Verification compares the one-shot relay report and separate browser readback; it proves transport/readback consistency, **not** that any target-site task succeeded. Approve-all, synthetic learning metadata, pause/resume replay, arbitrary navigation and form actions are disabled for this kind. `scripts/serve_desktop.py` requires all three explicit flags `--remote-entry-mcp-manifest`, `--remote-entry-profile-sha256`, `--remote-entry-task-file` with `--browser-tasks --desktop-browser --engine decider` (or fixture for a labelled synthetic test). The task file is private; do not put target profiles, account details or trajectories into source. The managed live session is not auto-upgraded.

The socket now requires possession of the per-relay token in addition to owner-only filesystem access and the public binding hash. A stale token or binding hash cannot fetch; tests also check that the token is absent from runtime status and the scheduled trajectory. This is **not** OS-level peer attestation: a sufficiently privileged same-UID/container process that reads worker memory or the temporary gate could still race the one response. The relay accepts an explicit cancellation event and removes only its own socket inode on stop while waiting for a request; an in-flight DNS/TLS fetch is not synchronously cancellable. The worker returns only the exact URL and SHA-256 fingerprints of a bounded title/first heading, not raw DOM text. The current test is uncredentialed, exact-entry, read-only and single-use. Do not use this primitive with private account pages. A production W1 path still needs account/tenant/consent enforcement, per-request redirects/subresources/method budgets and independent application outcome verification; W2–W6 also remain open. The underlying preflight now bounds the caller's DNS wait and slow HTTP headers by an absolute network-phase deadline; a timed-out resolver worker may continue briefly, without opening HTTP, until the system resolver returns.

Focused checks: `PYTHONPATH=src:tests .venv/bin/python -m unittest tests.test_web_https_relay tests.test_web_https_preflight -v`. Owned Ubuntu/Chromium tests are explicit: `AOS_DESKTOP_TESTS=1 AOS_HTTPS_RELAY_TESTS=1 PYTHONPATH=src:tests .venv/bin/python -m unittest tests.test_web_https_relay -v`. Real pinned Decider is a further opt-in with `AOS_REAL_BROWSER_TASK_TESTS=1`. The decision state now says that selecting `open_entry` **requests a separate human approval**, not that the model itself authorizes network access. With that truthful distinction, the unchanged 0.88 confidence gate admitted the pinned model's choice and a manually approved single synthetic TLS GET completed with independent readback. A separate 0.879-confidence engine test confirms the relay remains unopened below threshold. Neither result proves a user-provided website or account task. Canonical metadata and bounded observation contracts have synthetic examples at `schemas/web_https_relay.schema.json`, `examples/web_https_relay.json`, `schemas/web_remote_entry_observation.schema.json` and `examples/web_remote_entry_observation.json`.
