# W1 learning-event evidence foundation

This milestone is a **read-only metadata projection**, not the W1 background collector or a skill/dataset pipeline. `aos.learning_events.learning_events_from_database(path, run_id)` takes the existing bounded SQLite audit snapshot and derives one stable event per successful, recorded real-model call with the appropriate run-pinned deployment identity. A System-1 event additionally requires its linked decision. A System-2 event requires an actual pinned Bonsai call; a fixture supervisor or a run with no Bonsai call produces no Bonsai event. Vision calls without a linked plan remain explicitly unlinked. The projector does not call a model, execute tools, mutate the database, or persist events.

`schemas/learning_event_v2.schema.json` is the current event contract and `examples/learning_event_v2.json` is synthetic; v1 schema and fixture remain available for older projections. The report envelope remains version 1.0. The key is a digest of derivation version, role, run and call ID; v2 IDs differ from v1, while re-projecting an unchanged source across restarts returns the same v2 event. The event records source IDs, deployment identity hash, existing decision/escalation/verification references and blockers. It never copies request/response JSON, prompts, state, DOM, screenshots, action arguments, passwords, cookies or token values. A `verified_outcome` flag means only a linked System-1 action has an independently passed, matching verification with valid evidence references; it is **not** a gold label, completed episode, successful Supervisor plan, or permission to train.

For the bounded synthetic canvas path, v2 may attach an actual pinned Bonsai call to its capture artifact metadata and recorded `vision.scene` observation. It may also list independently passed downstream Decider verification IDs when the same-step decision uses that scene hash and the run-pinned System-1 deployment. These are provenance references only: the System-2 event still has no direct verification, `verified_outcome=false` and `training_ready=false`. Missing or ambiguous capture/scene/decision evidence leaves these references empty. This does not attribute a successful plan, create a Bonsai gold label, or license screenshot collection.

An explicit local review command is available for one already-recorded run. A separate [manual synthetic checkpoint](LEARNING_EVENT_OUTBOX.md) can persist this metadata for one exact role and source snapshot; it is not wired into tasks or a live queue:

```bash
.venv/bin/python -m aos.learning_events_cli --database /path/to/private-trajectory.sqlite --run-id RUN_ID
```

It prints one canonical JSON object with the snapshot hash, hashed run reference, bounded metadata events, and `collection_authorized=false`/`training_ready=false`. It does not list run IDs or discover databases. It rejects missing or corrupt sources, unsupported migration/schema versions, broken integrity, symlinks, invalid/missing run IDs and over 500 recorded model calls without partial output. Errors use a fixed message, never the private path or payload. The source opens read-only and is copied to a bounded in-memory snapshot before projection; the CLI never changes the source. Repeating it on unchanged SQLite content produces identical JSON. The snapshot hash can change if *any* source DB content changes, even outside the chosen run.

All events have `training_ready=false` and carry blockers for site-scope binding, collection rights, redaction, review and training authority. Current bounded tasks are also marked synthetic. Run snapshots are claims from the existing local trajectory store, not external attestation of model execution. The projector itself does not persist events; the separate manual checkpoint cannot advance when its source snapshot changes and does not recover after a source DB has been deleted. Neither proves site/tenant/role binding or consent, stores a live append-only event queue, produces reviewed skill/fine-tune candidates, or integrates into the task loop. Those remain W1/W3/W4 work; extending to real application content needs source-side minimization and explicit authorization before capture.

For every supported verifier, `verified_outcome=true` now requires a **separate successful readback action under the same decision**, with an observation matching that action's recorded result and the verifier's actual result. File read, form DOM, canvas outcome and local page each require their own expected effect/readback tool and observation kind. The fixed local two-page verifier additionally requires the exact Start or Details page projection and a fresh-shaped snapshot ID. A mismatched snapshot, wrong tool/kind/decision/result, or missing readback leaves `verified_outcome=false`; none creates a gold label. These remain synthetic-policy events with `training_ready=false`. Real Decider form/navigation S1 calls can be inspected; a real Bonsai vision call remains a separate S2 event without outcome attribution to a Supervisor plan. No Bonsai/S2 event is fabricated when the Supervisor was not called.
