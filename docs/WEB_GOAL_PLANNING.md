# Free-text goals against a scoped web skill catalog

## Current application pipeline (30 September 2026)

### Multi-parameter compiler and finite desktop runner (not deployed)

`web_goal_execution_binding.py` binds a typed proposal to an exact host-authored
development case and the existing multi-field form recipe compiler. The binding
includes scope/profile/task, source/review/release/selection/reuse identities,
every parameter, exact encoded form body, finite invocation and a separate
whole-record oracle contract. The oracle URL must equal the existing host-authored
state-plan URL; the module invents no endpoint and performs no default network call.

Exact human confirmation and fresh host source/control callbacks produce a
non-authorizing confirmation. A host-owned readback callback can compare every
field, not merely the scalar recipe marker; before/after source fencing and
bounded duplicate-free JSON checks reject partial, wrong-scope or uncertain
observations without replay. A reported POST count is only an observed field,
not independent trajectory proof.

The host-only `DesktopScheduler.configure_parameter_web_goal_execution` now
requires an already configured exact owned multi-field form, separate private
journal outside the tool workspace, current source loader and independent recipe
auditor. It verifies original desktop authority and holds/rechecks workspace FD
identity. It does not create a new scheduler, grant, model or network permission.
Unconfigured hosts remain denied; the ordinary form Start button cannot bypass
this path. Offline reviewed multi-field source preparation is now available via
[`scripts/aos-parameter-project`](OWNED_PARAMETER_PROJECT.md): plan → exact
request confirmation → provision → fresh manifest verification, with separate
CRM/inventory maps and real existing registry/compiler artifacts. Persisted
manual authoring is explicitly synthetic and unverified, not a fabricated
execution/review/release lineage. A separate explicit managed activation now
supports a CPU-fixture manual bootstrap, with retained source/listener pins,
immutable pre-action intent, original run binding and independent whole-record
receipt. It does not fabricate released-source provenance or enable native GPU
inference; model planning and released-source binding remain separate work.
Existing single-message reuse is unchanged.

Authenticated, bounded, duplicate-rejecting AOS operations are
`POST /api/tasks/parameter-web-goal/{preview,start,report}`. Preview requires
`schema_version:1.0`, `lease_id`, `generation`; start additionally requires exact
`confirm_sha256` and literal `human_confirmation:true`. Report requires only the
version and original `intent_sha256`, and is read-only under Human control.
There is no upload of arbitrary model-produced source, tool, URL or authority.

Start writes the immutable intent before the actual manager task. The existing
`RemoteFormOperator.form` executes the same six finite stages with fresh existing
human approvals. The runner binds the actual Browser child runtime separately
from its parent desktop authority, journals the original run before tools and
checks source/control again at gateway dispatch, including runtime startup and
read-only observation. Timeout, cancellation, failed audit or lost acknowledgement
retains unresolved intent across fresh journal instances; no automatic replay.

Explicit owned record mode commits the actual parsed submitted fields, emits a
bounded whole-record object alongside the existing scalar state marker, and
permits one extra authenticated TLS GET from the same pinned state URL. The
manager validates exact original trajectory audit pins before this one-use read.
Only a matching succeeded original task, typed recipe trajectory audit and all
record values can produce an accepted immutable receipt. Historical hash-only
inspection does not infer native model use, site account rights, training or GPU
release. Readback alone remains `host_reader_record_binding_only`; broader receipt
scope is `synthetic_bound_run_and_whole_record`, with site/training/GPU false.

The EN/TR Tasks panel is source-wired for trusted configured hosts: explicit
parameter preview, separate confirmation and read-only receipt inspection. It
does not silently activate a host source provider or update the live UI. Two
different synthetic applications and multiple native inputs remain required
for final acceptance; CPU/mock/loopback evidence cannot close that gate.

### Optional reviewed knowledge for free goals

Prepared input or an older proposal without an acknowledgement never proves
model use. New knowledge proposals record a separate immutable acknowledgement
only after actual native request/response equality checks. The report validates
the sidecar's intent/planning/bundle/context/request/response/deployment hashes;
fixture acknowledgement stays `real_model: false` and actual use unverified.

Historical binding survives later source revocation/expiry/control/model changes;
current source/review and **current planning admission** are reported separately.
Busy/Human/paused state may invalidate fresh planning admission without proving

Semantic relevance, downstream outcome, training/activation/authorization and

### Unacknowledged start blocks admission

A durable start-review without its exact accepted job receipt reserves the
existing desktop scheduler, including ordinary task and model admission. Only
the synchronous start matching that immutable review can temporarily enter its
own reservation; the exception is cleared even when start raises. Cancellation
does not erase uncertainty. The EN/TR panel exposes this state and the API asks
the operator to inspect the task timeline rather than incorrectly claiming that
execution never started. No automatic retry, receipt fabrication or reset exists.
This is local admission safety, not a Scientist GPU release acknowledgement.

The panel also offers explicit **Recover existing task acknowledgement**. The
operator supplies and confirms the existing timeline task ID. The authenticated
`recover-start` route checks fresh original session/runtime/lease/generation,
the immutable pending review, a stored `browser_remote_form` job and exactly one
existing execution bound to that review's preview and created after the recorded
synchronous start attempt. Pre-existing jobs with the same preview cannot be
substituted. The attempt fence is process-local, so restart cannot fabricate it.
It only writes the missing
acceptance receipt; it never invokes a model, tool, start or retry. Wrong tasks,
changed authority, ambiguous bindings and repeated recovery are rejected without
opening admission. Restart-lost history or changed control remains blocked;
there is no general reset. Recovery does not prove task success; the separate
independent result readback remains required. Canonical recovery request/receipt
schemas are provided. Native/GPU/managed deployment acceptance remains unrun.

## Implemented boundary

`BonsaiWebGoalPlanner` is a separate, proposal-only System-2 adapter. It accepts free-text goals rather than the two exact owned-save-message forms. One immutable catalog identifies one application/tenant/role/profile and up to eight skills. Each skill carries exact skill/task/recipe/release/selection hashes, a description and up to eight bounded text parameters, optionally restricted to enumerated values.

The host creates a per-catalog response grammar: select one catalog skill and every required parameter, or return `needs_human`. Unknown skills/parameters, foreign catalog hashes, extra fields, missing/true/nonboolean permission flags, invalid bounds, duplicate JSON keys and unsupported parameter values are rejected. Unicode and quoted text are not normalized. Descriptions and goals cannot add a URL/tool/action field or broaden authorization.

The generic planner still does **not** independently authorize a site/account or start System-1. Catalog hashes supplied in the synthetic example are placeholders, not reviewed source admission. `scope_authorization_verified`, execution/activation/training flags remain false.

## Selected owned-source bridge (30 September 2026)

`DesktopScheduler.owned_web_goal_catalog` builds a one-skill catalog from the
existing current reuse admission, reviewed release/selection, candidate source,
stored profile and task. It uses the existing source/control checks; request or
model descriptions cannot choose a URL, tool, review or release. This first host
bridge supports the already implemented **owned synthetic save-message** recipe,
not the generic contact/inventory example catalogs or arbitrary real sites.

Authenticated, Origin-checked `POST /api/tasks/owned-web-goal/catalog` takes
`schema_version: "1.0"`, current `lease_id` and integer `generation`; it returns
the catalog and exact digest. The corresponding `/preview` takes the same fields
plus typed `proposal` and `confirm_catalog_sha256`. Canonical request schema:
`schemas/owned_web_goal_request.schema.json`; nested proposals additionally obey
`web_goal_plan.schema.json`. Both are bounded, duplicate-key rejecting requests.
There is no `/start` or model call in either route.

Preview rechecks current catalog/control, rejects abstention or changed sources,
and maps the one parameter to the existing deterministic selected-candidate
preview. Exact ASCII message limits remain enforced before that compiler;
Unicode, quotations, path characters and leading/trailing spaces unsupported by
the current executor are rejected, never normalized or silently substituted.
The existing preview/review, fresh execution approval, intent, fixed six-stage
executor and independent readback remain required. A proposal preview is not an
executed task, a new planning admission or proof that free-text semantics match.

25 targeted CPU tests pass in 0.192 seconds:
`data/owned-web-goal-bridge-20260930.log`. These use synthetic source providers and
mock compiler results, plus actual authenticated ASGI routes; they prove mapping,
stale selection/control, mid-preparation source mutation, scope/input rejection,
zero new runs and no inference/POST execution. They do not prove live registry,
real model quality or browser/GPU acceptance. No managed-instance deployment ran.

## Model and lifecycle

The separate deployment pins protocol `aos-web-goal-plan-v1`, canonical response schema, exact system-prompt digest and a 1,024-token output bound. Existing recovery and owned-skill deployment identities do not change. Native inference reuses the pinned Bonsai process/cleanup path. Prompt/schema drift is rejected before inference; a changed prompt requires a different deployment identity.

Calling `plan` requires exact inference consent and a host `current_catalog` provider. The provider must return a typed current catalog equal to the frozen request snapshot before scheduling, immediately before dispatch and after response. The adapter composes the pre-existing dispatch hook first and restores its exact presence/value after success, failure or cancellation. Concurrent use of one planner is rejected. The supplied evidence is copied before await so another caller cannot replace the dispatched catalog.

This freshness callback is a seam for host-owned source validation, not a built-in external ACL or source attestation. The caller must implement registry/review/source checks before admitting a real catalog. A model proposal may contain valid parameter text that is nevertheless semantically wrong; separate host preview, fresh execution consent and independent effect verification are still required.
