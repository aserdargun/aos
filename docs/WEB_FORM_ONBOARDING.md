# Console HTTPS form onboarding — narrow W1 slice

The authenticated **Web applications** screen prepares a stateless HTTPS form task and plan without contacting the target. Select a registered staging/production profile, enter a task key and verifier reference, preview the task, and confirm its exact SHA-256. Then enter canonical same-origin POST and receipt URLs, choose one field or 2–8 ordered fields, and enter **non-secret** test values. The row order must match the form's DOM order. Preview and confirm the plan SHA-256 separately. Each edit or mode change invalidates the corresponding preview or receipt.

`form-task-preview` and `form-plan-preview` write nothing. Registration writes immutable canonical task/plan JSON and the input to separate owner-only directories under ignored `data/` (`0700` directories, `0600` files). Single-field input is raw text; multi-field input is the existing canonical `web_https_form_fields` document, ordered and bound to exact body SHA-256/byte count. The UI clears values after registration and does not show them in the receipt, commands, approval text, or plan JSON. **Do not enter passwords, cookies, tokens, customer records, or other sensitive data.** The private input files and low-entropy body hash are not redaction; the operator must remove the original input file after use. Registration does not authorize execution, collection, or training.

For a public hostname, the four-approval mode displays `./scripts/aos-v1 preview-remote-form ... --remote-form-public-plan-sha256 <exact-plan-sha256>` and a separate `start` command after safe shutdown of the current managed session. The six-approval state mode displays `preview-remote-form-state` instead; the base preview rejects state-plan flags rather than silently validating only the form. Single-field commands use `--remote-form-field-name` and `--remote-form-value-file`; multi-field commands use only `--remote-form-fields-file`. The UI does not run either command. The manager revalidates the registered profile, task, plan, input, and exact public grant before a **new** session; starting alone makes no target request. The base task requires four distinct manual action approvals for entry GET, fill, one POST, and receipt GET. `.invalid` profiles may be used for synthetic draft tests, but the public manager path rejects them.

For the optional six-approval **before/after state readback**, select that mode before registering the task. It fixes the task budget at six actions; an existing four-action task cannot be upgraded. After registering the form plan, enter a canonical same-origin state GET URL and different expected before/after HTML SHA-256 digests. An optional unique HTML marker `id` and its different before/after normalized-text digests may be pinned too. With the marker triplet, the optional exact submitted-field selector requires the after-marker hash to match that private field's normalized value. The manager rechecks this offline before a new session, and the runtime fails closed before networking on mismatch. Preview writes nothing; a separate exact state-plan SHA-256 confirmation writes one canonical `0600` plan under the ignored private `data/` root. The public manager commands remain hidden until this state plan is registered, then include both `--remote-form-state-plan-file` and `--remote-form-public-state-plan-sha256`. Preview does not contact the target, and neither registration nor the displayed command authorizes a GET. The two additional GETs each need their own task approval; even a submitted-value/readback match is not durable or independent semantic application-outcome verification.

This screen does not cover login/session/CSRF, JavaScript-dependent forms, semantic application outcome, external authorization or data-rights review. Multi-field runtime still accepts only the bounded control types described in [WEB_HTTPS_FORM_TRANSPORT](WEB_HTTPS_FORM_TRANSPORT.md); it is not a general form automation system. Real-site W1 acceptance remains open. [Evidence](STATUS.md).

The six-approval state path is also exercised end-to-end on an owned `.invalid` TLS fixture: the same no-network task, form, value and state registration functions used by the console write private artifacts, and the visible Ubuntu/Chromium/Playwright MCP scheduler consumes those exact objects. Fixture and pinned real-Decider modes both require six distinct approval responses, one POST, two state GETs and independent readback. This proves the registration-to-runtime contract on a synthetic site, not public manager `start`, account access or semantic outcome.
