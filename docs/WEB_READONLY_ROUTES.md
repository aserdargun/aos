# W1 read-only route plan and host fetch

The authenticated Web applications panel can now prepare the same immutable plan without manually writing the URL source file. Choose a registered staging/production profile and 2–8 planned pages when previewing its task draft; confirm that task's SHA-256 to create its private `data/web-task-drafts/<sha256>.json` file. Enter the ordered exact URLs (first must be the stored entry URL), preview their plan hash, then separately confirm it to create `data/web-route-drafts/<sha256>.json`. Preview makes no site request or file write. The server reads its own private task path by exact hash, rechecks canonical content and the stored profile, runs `plan_web_readonly_routes`, and never accepts an output path from the browser. Both stores are owner-only, content-addressed and immutable; a damaged existing file fails closed. The two returned paths are inputs for `aos-v1 preview-remote-routes` and a later explicitly pinned `start`, not a hot configuration of the running session. The verifier reference remains a label, not an independent site outcome oracle. The CLI route-source workflow below remains available for advanced/manual cases.

An explicit owned integration test now takes the **authenticated API's actual private task and plan files**, passes both through the managed `prepare_remote_entry`/`prepare_remote_routes` admission checks, and starts an isolated pinned Ubuntu/Chromium/Playwright MCP scheduler with the parsed bytes. Real pinned Decider makes four successful S1 calls over two two-route tasks; four separate approvals and independent readbacks pass. The target is still a local synthetic TLS fixture behind patched public DNS. The test does not use the live managed 8765 session or prove a user-owned site's account, data rights or application outcome.

`plan_web_readonly_routes` binds an ordered list of **two to eight exact HTTPS URLs** to one immutable registered staging/production profile and canonical `WebTaskContract`. The first URL must be the registered queryless entry; every later URL must be canonical and on that same origin. Later routes may use a fixed canonical query of 1–8 unique `key=value` pairs, at most 512 encoded ASCII bytes and printable ASCII values of at most 128 characters. This is for non-secret static filters only: exact route URLs are stored in private plans, approvals and operator UI; the validator cannot detect tokens or personal data. Never put those in a query. The task's page, navigation and action budgets bound the **number of listed routes**, not the number of times the host function can be called. Duplicate URLs, malformed/duplicate query parameters, fragments, percent-encoded paths, redirects, alternate origins and local/private profile environments are not admitted. The plan carries the profile/task hashes and explicitly grants no execution or collection authority. It is not a skill or a discovered site map.

`fetch_web_readonly_route` requires a fresh exact plan SHA-256 confirmation and explicit route index before each host-side GET. It reopens the profile, revalidates the task and plan, then sends the exact path and query under the existing public-IP DNS, selected-IP TLS hostname, absolute deadline, non-redirected `200 text/html` and 65,536-byte response rules. The report contains only hashes, index, byte count and false authority flags; the body is returned only to the in-process caller. No cookies, Authorization headers, client headers or POST body are sent. The canonical [plan](../schemas/web_readonly_route_plan.schema.json), [fetch report](../schemas/web_https_readonly_route.schema.json) and [synthetic example](../examples/web_readonly_route_plan.json) travel together.

`ExactReadOnlyRouteRelay` adds an owner-only Unix socket and a fresh per-session client token. The host must explicitly `arm(index)` in plan order; without an arm, a socket request is denied without a site GET. Each matching accepted request consumes that arm **before** the host fetch, so a failed or uncertain fetch is not retried. A completed route cannot be fetched again, and the relay closes after the finite plan, cancellation, timeout or request-attempt exhaustion. The separate `readonly_route_page_gate_source` allows only main-frame document GETs whose complete URLs, including any query, are listed in the plan; all subresources and off-plan requests are aborted. Bodies are hash-checked and fulfilled with no-script/no-form CSP. A labelled opt-in test used the pinned MCP CLI in one owned, visible, network-none Ubuntu Chromium session to open `/entry` and `/details?view=compact&page=1`, with a host arm between them. The target was a temporary local TLS fixture behind patched public DNS; no external site was contacted.

`DesktopReadOnlyRoutesMCPRuntime` now binds that plan to an application-owned, pinned MCP worker in one owned visible browser. It rechecks the profile, task, plan and live runtime pin at startup and each action; the worker accepts only ordered `browser.remote.route` and bounded `browser.remote.observe`, and its handshake confirms the route-list hash. Each later route requires a fresh readback of the preceding route; arbitrary MCP tools and replay are rejected. The host relay still independently validates every exact GET. The route observation includes content-free URL/title/H1 hashes plus a bounded sample of DOM anchors represented only by already approved route indices, unregistered-anchor count and truncation bit. It does not navigate links or return unknown targets; the v1 page fingerprint remains URL/title/H1 only. The owned transport test uses only the temporary local TLS fixture and patched public DNS, not an external site or a model decision.

The opt-in `browser_remote_routes` scheduler task binds the plan, live MCP runtime and run in append-only migration `0013_remote_readonly_routes.sql`. It keeps approve-all and learning metadata disabled, records a separate expiring action approval before **each** route, and only then starts/arms the host relay. Each route gets a separate bounded URL/title/H1 hash readback and verification record before the next approval. Pause, takeover, rejection or failure cancels without replay. Managed `aos-v1 plan-remote-routes` reads an owner-only newline-terminated URL list under ignored `data/`, validates the stored profile/task and writes a new canonical owner-only plan in a `0700` private directory without network access or overwriting an existing file. It prints exact URLs for operator inspection; URLs are not secret credentials, but path names may still be sensitive. Managed `start` canonical-copies the plan into a new private session and pins its SHA-256; `preview-remote-routes` validates without starting or fetching. The existing one-entry task is unchanged.

An explicit opt-in scheduled test also uses the pinned real Decider for two fresh decisions and two separately approved routes in the same owned Chromium/MCP session. Its target remains synthetic local TLS; no real site, account or Bonsai inference is involved.
Unmocked host Playwright console tests submit the route task, wait for each approval and verify that no GET precedes its corresponding click. One uses the fixture decision engine; a separate explicit test uses the pinned real Decider and records two successful model calls. Both stay behind the same synthetic TLS boundary, not an external target.

**Still not a product web-app workflow:** direct calls to standalone host fetch or relay `arm` are not persisted human approvals; they must only be used for a separately authorized test target. The scheduled task observes a bounded inventory of already planned links but does not discover or authorize new routes, click, fill forms, authenticate a tenant, collect learning events or verify an application outcome. A GET is not assumed side-effect-free. The standalone host fetch has no aggregate request counter; the scheduled route task instead uses its finite immutable plan and one-use relay. Genuine target URL, account, authorization, data rights and an independent site-specific task oracle are still required for W1–W6 acceptance.
