# W1 bounded HTTPS form transport prototype

`aos.web_https_form_transport` adds an exact profile/task-bound plan for an entry GET, one form-urlencoded POST and a separately read receipt GET. The plan stores only the SHA-256 and byte count of the POST body, not its bytes. All URLs must be canonical HTTPS paths on the profile's exact origin; the task must explicitly include navigate, fill, click, snapshot and verify tools and sufficient action/page budgets. The plan is a draft, never an execution grant.

The transport accepts `.invalid` synthetic hosts by default. A non-`.invalid` public HTTPS hostname additionally requires the exact plan SHA-256 in the separate `confirm_public_plan_sha256` backend parameter; a missing, stale or mismatched grant fails before networking. Both modes require an explicitly supplied hostname-verifying TLS context. Managed public mode uses the system CA store and does not allow a custom CA file. This code-level grant does **not** establish that the operator has permission to use a real site. A managed opt-in path exists for one bounded static Cookie request value, but no browser login, session refresh or site-specific outcome oracle exists. The standalone caller must provide a fresh approval-consumption callback that returns literal `True` for each exact request hash. The scheduler arms an in-memory single-use permit only after the corresponding action's approval row is durably `consumed`; that permit expires at the action's remaining deadline (at most 90 seconds), measured with a monotonic clock. A wrong request hash, replay or elapsed deadline consumes/denies the permit before a host request. It is not persisted or reusable after restart. The standalone callback remains the caller's responsibility and is not automatically deadline-bound.

Each request is one-shot. Entry GET and receipt GET reuse the bounded host HTTPS probe: public-IP DNS gate, selected-IP TLS hostname verification, no redirect, `200 text/html`, 65 KiB response and deadline. POST sends at most 4 KiB of exact in-memory bytes with fixed form content type and accepts only `302` or `303` with a `Location` resolving to the single planned receipt URL. Neither response is followed implicitly; the status is treated solely as an exact receipt pointer, not as a site outcome. `301`, `307`, `308`, missing/changed/cross-origin locations and non-identity content encoding fail closed. A POST failure or uncertain response consumes the POST attempt; it is never retried. Receipt GET needs its own approval and can be denied after a POST, leaving the site outcome unknown. Optional static Cookie is sent only to the exact same-origin host requests, including the separate state GET if configured. Set-Cookie processing, Authorization headers, arbitrary headers, login and credential-vault integration remain absent.

The transport rechecks the original pinned plan SHA-256 at each network stage; swapping in another otherwise-valid in-memory plan cannot retarget a previously confirmed session.

`ExactHTTPSFormRelay` exposes only the three planned requests through an owner-only Unix socket with a fresh client token. An opt-in Playwright MCP page gate in the network-none visible Ubuntu Chromium intercepts only main-frame document requests in exact GET→POST→GET order, checks the POST bytes against the host plan and aborts subresources/off-plan URLs. The gate requires the same exact public plan grant before accepting a public hostname. It fulfills the POST as local `204` after the host accepts only an exact `302` or `303` receipt pointer, leaving the browser on the form until a separately approved explicit receipt navigation. `DesktopHTTPSFormMCPRuntime` owns a pinned worker in the owned Ubuntu desktop. It binds the canonical draft to live runtime/image/bundle/worker hashes, checks the exact single-field body before startup and at each stage, passes private value/token over stdin rather than process args, and exposes only ordered open→fill→submit→receipt→observe actions. Its startup handshake attests the public plan hash (or `null` for synthetic mode). The worker checks the actual form action, method, one required text or email input and one enabled in-form submit control before MCP fill/click; it uses fresh snapshot references and returns only contentless page hashes or stage/body hashes.

`DesktopScheduler` offers opt-in `browser_remote_form` **only when constructed with** the stored remote profile/task, exact `WebHTTPSFormPlan`, private field name/value and verifying TLS context. Public targets also require `remote_form_public_plan_sha256` equal to that exact plan hash. `./scripts/aos-v1 plan-remote-form` creates a new owner-only canonical plan offline from an owner-only single-line value file, without printing its contents; `preview-remote-form` checks the exact grant without starting a session or contacting the target. A controlled new `start` copies plan and value to owner-only session files; the supervisor and backend revalidate scope, hashes, input and system TLS before advertising the task. The raw value is never in argv or status. After the backend terminates, including failed admission or failed backend exit, the manager unlinks only its copied value file; verified previous-boot recovery also unlinks it after confirming the old runtime is stopped. This is not secure erasure, does not remove the operator's source file, and cannot remove a copy while an unconfirmed backend remains live. `RemoteFormOperator` runs four distinct decision/policy/approval cycles: entry GET, fill, one POST, receipt GET. `Approve all` and resume are forbidden. Before arming each host network request, it checks that the exact action's approval is durably consumed; the host callback then consumes an in-memory one-shot permit. The append-only `0014_remote_https_form.sql` binds job/run/profile/draft/plan/live child runtime identity; raw form value and relay token are not stored in the trajectory DB. A separate browser receipt readback and host report must match for **transport-level** success. Rejected submit approval leaves zero additional POSTs; no retry follows an uncertain POST. The EN/TR console advertises the synthetic/public mode, exact URLs, field name and body hash only when the backend is configured; the current managed session was not upgraded.

Each approval action includes its stage-specific canonical HTTPS target URL. Fill and submit also show the field name, and submit shows the exact planned body SHA-256; the private value and body bytes stay out of the approval record. The operator and runtime derive the same arguments from the plan, and the runtime rejects any changed target or body hash before execution. The UI renders these fields and explicitly asks the operator to check the target before approving. A public plan grant and these approvals are bounded execution gates, not evidence of account/data rights or semantic safety of the submitted value.

`receipt_response_read` proves only transport of a receipt HTML response, **not** that the application saved the intended state or that an account/tenant was verified. The 1.1 host report includes the accepted upstream POST response status (`302` or `303`) as contentless transport provenance; the browser still sees only the relay's local `204`. The report is not itself a durable trajectory attestation. It remains transport-only (`browser_connected=false`) even when the separate owned browser test passes; it does not include or attest that browser identity. It omits body bytes, raw URLs, cookies and credentials and leaves `account_verified`, `site_outcome_verified`, `collection_authorized` and `training_ready` false. The caller must not treat HTML text as authority. Canonical contracts and synthetic example: `schemas/web_https_form_plan.schema.json`, `schemas/web_https_form_transport.schema.json`, `examples/web_https_form_transport.json`.

The owned synthetic TLS tests check separate approval refusals before network, exact body/plan binding, `302` and `303` one-POST receipt pointers, `307` and cross-origin/changed redirect rejection, public-host denial without an exact grant, private socket cleanup and no replay after uncertain POST. An owned public-**looking** `example.com` hostname with a local test certificate and patched DNS/socket path exercises the granted worker and four-approval scheduler paths; it makes no external site request. The managed plan/preview/private-copy tests and isolated backend/EN UI advertisement test also make no target request. The scheduler test verifies four consumed manual approvals, denial before a second POST, append-only plan/run binding, no raw private form value in DB and separate transport readback. Beyond the bounded static Cookie option, W1 still needs a real credential lifecycle, target-site auth/session and redirect/subresource policy, and a site-specific independent **application outcome** verifier. Real target URL, authorized account, permitted task and data rights are still required before W1 product acceptance.

The `DesktopScheduler`/`RemoteFormOperator` path also accepts an explicit ordered list of **two to eight** `{name,value}` fields instead of its legacy single field. The pinned worker requires exactly one POST form, the same number and DOM order of required enabled `input[type=text]`, `input[type=email]`, `textarea` or single-value `select` controls plus any explicitly declared, value-pinned in-form hidden input, unique associated labels and one enabled submit control: explicit/default `<button>` or `<input type=submit>`. The submitter must be inside the form, unnamed, without `formaction`/`formmethod`/`formenctype`/`formtarget`/`formnovalidate` overrides; the form target must be empty or `_self`. It inspects all form-associated controls, including ones outside the form element, rather than only descendants, and checks effective disabled state including disabled fieldsets. It batches adjacent text/email fields through visible MCP fill calls and uses pinned MCP select-option for an exact, unique enabled option value; multiple, disabled, absent or duplicate-value options fail closed. It independently checks all planned values and native control validity before the one approved submit; an invalid email never reaches the host POST. The exact ordered URL-encoded body remains bound by the existing plan hash; approval actions show only comma-separated field names and body hash, never values. A declared static hidden input is accepted only inside the form, in exact field order and with an exact pre-pinned value; the worker never fills it. Undeclared, changed or externally associated controls, duplicate name/label or mismatched body fail closed. Password inputs remain unsupported; this does not extract, refresh or authorize dynamic CSRF tokens. The canonical private-input shape and explicitly synthetic example are `schemas/web_https_form_fields.schema.json` and `examples/web_https_form_fields.json`; never commit real field values. Offline `aos-v1 plan-remote-form-fields` accepts only an owner-only JSON list of fields and writes a new canonical `0600` document with computed body/hash and false authority flags, without echoing values. Managed plan/preview and safe **new** start accept that document as `--remote-form-fields-file`; its session copy is hash-pinned, rechecked by supervisor/backend and removed on the same lifecycle as the legacy value file. The UI shows field names only. Owned direct Chromium execution and managed backend/UI admission were tested separately; no real managed-site execution is claimed. This does not add a dynamic workflow, authentication, account verification or site-specific outcome proof.

An opt-in `aos.web_https_form_state_probe` draft binds a fourth, distinct same-origin HTML URL and operator-declared before/after response SHA-256 values to the exact form plan. On the **same** `ExactHTTPSFormTransport` instance, it permits one separately approved GET after entry but before POST, and one separately approved GET only after successful receipt readback. Phase and state-plan hash make the two approval digests distinct even though the URL is identical. Public hostnames also require a separate exact **state-plan** grant in addition to the form-plan grant; synthetic `.invalid` hosts reject that extra grant. It reuses the public-IP/TLS/no-redirect/size/deadline probe. A mismatched response or uncertain GET consumes that phase's one attempt; no write is retried. The report contains only URL/receipt/response hashes and byte counts. It asserts only `declared_response_transition_observed=true`; `account_verified`, `site_outcome_verified`, `collection_authorized` and `training_ready` remain false. A changed HTML response can be unrelated to the intended save, and operator-declared hashes are not an independent application oracle. Canonical contracts and synthetic example: `schemas/web_https_form_state_plan.schema.json`, `schemas/web_https_form_state_report.schema.json`, `examples/web_https_form_state.json`.

For a narrow HTML marker check, planning may additionally take all three `--remote-form-state-marker-id <id>`, `--remote-form-state-before-marker-sha256 <hash>` and `--remote-form-state-after-marker-sha256 <hash>`. The hash is `digest({'text': ' '.join(element_text.split())})` for exactly one closed HTML element with that ID, at most 512 normalized characters. `aos.web_https_form_state_probe.form_state_marker_sha256` computes it from owned, authorized HTML; do not commit or paste private page content. Missing, duplicate, incomplete or mismatched markers fail closed without retry. The optional marker ID and both expected hashes are part of the exact state-plan grant and append-only plan JSON. Each state approval shows the marker-ID hash and phase-specific expected text hash, never the text. The report adds marker hashes and `declared_marker_transition_observed=true`, while `site_outcome_verified=false`: a site can show a marker without persisting a business change. This is not account/tenant verification or an independent site-specific outcome oracle. Legacy plans omit these optional fields and retain their original hashes.

With the marker triplet, `--remote-form-state-submitted-field-name <exact-field-name>` may opt into a stricter binding. The offline manager and runtime compare the selected private field's whitespace-normalized value to the declared after-marker text hash, while rechecking the exact URL-encoded form body hash and byte count. A missing, ambiguous or mismatched field fails before any network request; the field name itself is hashed in approval/report metadata. A matching separately approved after-state readback adds `submitted_value_readback_verified=true` without exposing the value. This proves that the declared marker text matched one submitted value in that readback, **not** durable application state, account identity, tenant scope, or an independent semantic outcome. Existing state plans without this option retain their previous hashes and behavior.

The scheduler can receive an exact optional state plan and separate public state-plan grant. This keeps the old four-action task unchanged when absent; when present, the same `browser_remote_form` task performs six distinct Decider/policy/durable-approval/gateway actions: entry, host state-before GET, browser fill, one POST, browser receipt, host state-after GET. The two host GETs never enter the Chromium page gate. The runtime requires the baseline before fill; an append-only `0015_remote_https_form_state.sql` row binds the state plan to the form job/run and live child runtime, and each approval rechecks it. The EN/TR console displays the exact state URL/plan and six-stage progress when the backend advertises them. Owned local TLS/Ubuntu/Chromium/MCP fixture tests cover direct execution; manager tests cover offline plan/preview/private-copy/argv/backend-admission boundaries, not a real target.

Managed public form state is opt-in. After preparing the exact form plan/value described above, run `./scripts/aos-v1 plan-remote-form-state` with the same profile/task/form-plan/field/value options and `--remote-form-public-plan-sha256 <form_hash>`, plus `--remote-form-state-plan-file data/<private-state-plan>.json`, `--remote-form-state-url https://<authorized-host>/state`, `--remote-form-state-before-sha256 <expected_before_html_sha256>` and `--remote-form-state-after-sha256 <expected_after_html_sha256>`. The command creates a new owner-only canonical `0600` draft without a request and returns the exact `state_plan_sha256`. Then use `preview-remote-form-state` or a **new** `start` with the same profile/task/form/field/value/form-grant/state-plan-file options, omit the URL/expected hash options, and add `--remote-form-public-state-plan-sha256 <state_plan_sha256>`. Preview makes no target request; start pins a private session copy and revalidates it in supervisor and backend. A running session is never hot-upgraded. The current live managed session has not been restarted or used with this option. Operator-declared HTML hashes are not an independent outcome oracle; no site-specific semantics, account proof, data rights or W1 acceptance follow from this prototype.

The optional static Cookie path is separate from the form value. An authorized operator supplies a header **value only**, such as `session=...`, with no `Cookie:` prefix and no trailing newline in a private owner-only `0600` file under `data/`. `plan-remote-form-cookie` validates the exact public form inputs and Cookie syntax offline, returning only its SHA-256; `preview-remote-form-cookie` requires that SHA-256 and makes no request. A new `start` with the same form inputs plus `--remote-form-cookie-file <private-file>` and `--remote-form-cookie-sha256 <exact-hash>` copies it to the private session and pins it through supervisor and backend. The secret is not in argv, status, approval, trajectory DB or report; only the hash is, including in each approval action. The manager removes its private session copy after confirmed backend exit, certain failed launch before the supervisor starts, or safe previous-boot recovery, not the operator's original. This is not secure erasure. An append-only `0016_remote_https_form_cookie.sql` row binds hash/form/job/run/live browser runtime; every scheduler gateway check revalidates the in-memory value against it. Cookie syntax excludes control characters, header injection, duplicates and values above 2 KiB. Browser worker never receives the request header directly. Host HTML GET now rejects a response before returning it to the relay or state probe when it contains any nonempty Cookie value or name/value pair in raw, HTML-escaped or percent-encoded ASCII form. A rejected entry/receipt/state read is consumed and does not retry a POST. This is only a bounded exact-reflection guard: transformed, split, encoded-in-other-ways or script-generated disclosure remains possible, and benign matching page text may be rejected. Do not use this mode on untrusted content. Cookie expiration, Set-Cookie rotation, CSRF and full login flows are unsupported; a static Cookie is not proof of account or tenant identity. Owned public-looking TLS/DNS fixture tests cover exact entry/POST/receipt/state requests, four-action scheduler approvals, private-copy/CLI guards, reflection rejection and no raw secret in DB. No real external site was contacted; W1–W6 remain open.
