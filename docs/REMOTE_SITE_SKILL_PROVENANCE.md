# W3 remote route skill source binding — read-only

`aos.remote_site_skill_provenance` joins one **manual, immutable S1 skill draft** to one completed `browser_remote_routes` run and one exact route index. It checks the draft's claimed S1 model-call events and canonical request hashes, pinned deployment, profile, task, route plan, manual page draft and the route's approved HTTPS GET plus separate browser readback. The event's decision must be the selected route action's decision, not merely a call elsewhere in the same run. The learning-event and route audits reuse **one frozen SQLite snapshot**; changed sources fail closed. An already superseded profile or page draft is rejected.

```sh
PYTHONPATH=src .venv/bin/python -m aos.remote_site_skill_provenance \
  --database data/<private-trajectory>.sqlite --run-id RUN_ID \
  --profiles data/web-applications --pages data/site-knowledge \
  --skills data/site-skills --skill-sha256 SKILL_SHA256 \
  --selected-plan-sha256 PLAN_SHA256 --route-index 0
```

The canonical report is `schemas/remote_site_skill_provenance.schema.json`; `examples/remote_site_skill_provenance.json` is **synthetic**. Output includes hashes, route index and source event IDs, never raw URL, DOM, model request, Cookie or skill steps. Treat even hashes and IDs as private metadata. The report explicitly distinguishes `transport_readback_verified=true` from `site_outcome_verified=false`: a successfully fetched/read-back page is **not** a completed application workflow. Manual page/skill semantics, parameter values, account/tenant access, data rights, review, skill execution, activation, collection and training are not established. Remote routes do not call Bonsai, so this S1-only check cannot produce an S2 skill or dataset. It makes no new network request and does not change a running session.

The authenticated EN/TR Tasks panel can inspect one registered private S1 draft by its exact SHA-256, a successful real-S1 route run from the current managed session, and a route index. `GET /api/tasks/skill-drafts` defaults to S1 and accepts only one exact `model_role=system1` or `model_role=system2` query. Both lists are integrity-checked and filtered to the server-pinned profile; the separate S2 list is **inventory only**, never an input to S1 route inspection. The lists contain private skill keys/revisions/hashes, not steps, parameters or source events. `POST /api/tasks/skill-source-inspect` accepts only the three explicit selection fields; the server pins the database, profile, plan, page and skill stores and shares the route audit concurrency gate. An S2 draft fails this S1-only inspection. The inspection UI shows only the S1 draft hash, route index, source-event count and the transport-only warning. Neither endpoint exposes URLs/DOM/request bodies or makes a network request. A listed draft is not automatically bound to the selected run: the operator must choose its actual source run, and mismatched or changed sources fail closed. This is read-only historical inspection, not approval, execution, activation or training. Route runs do not call Bonsai, so an S2 draft appearing in the inventory has no verified S2 source or outcome.

An owned synthetic TLS/Ubuntu/Chromium/MCP test uses a **real pinned Decider**, asserts one snapshot, and rejects a wrong plan, wrong route, wrong task and an event from the other route. This removes a redundant database backup, but does not establish a measured end-to-end latency gain. The other source assertions are structural; no real target site or independently varied skill execution is claimed. W3 and W1–W6 product acceptance remain open.
