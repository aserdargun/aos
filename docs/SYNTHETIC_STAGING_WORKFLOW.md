# Opt-in synthetic staging web-app workflow

`browser_staging_workflow` is a fifth, **explicitly opt-in** fixed task for exercising a small local web application through the owned Ubuntu/X11/Chromium/Playwright MCP runtime. It is not a user-supplied site, authenticated tenant, general browser agent, or collection/training grant. The four-task managed `./scripts/aos-v1 start` default remains unchanged; an already running session is not restarted or upgraded.

## Scope and task contract

Start a separate isolated console with `--browser-tasks --desktop-browser --desktop-staging-mcp-manifest models/desktop-mcp-v001/manifest.json` and an explicit decision engine. The MCP package must pass its existing pinned bundle check. `GET /api/tasks` lists `browser_staging_workflow` only when the staging flag is configured and reports `staging_transport=playwright_mcp`; the existing browser form may remain CDP. `POST /api/tasks` accepts this fixed kind with the current lease/generation. `approve_all=true` is always rejected for it.

For an isolated test console only, add `--staging-fixture-port <unused-container-loopback-port>` to bind the fixture and Chromium HTTP proxy to one explicit nonprivileged port. The port must be supplied together with the staging MCP manifest; a conflict fails rather than switching ports. The managed pilot does not set this option by default, and the live session is not hot-upgraded. Pinned mode does not bind a real web profile or grant external network access.

The managed local pilot also accepts `./scripts/aos-v1 start --synthetic-staging` for a **new** session after safe shutdown of any running pilot. This pins the prepared MCP bundle to the fifth task while preserving the default four-task mode. Repeating `start` against an already-running default session with a different staging selection fails rather than hot-enabling it. The current managed user session is not restarted by this source change.

The worker binds a private ephemeral `127.0.0.1` HTTP server before Chromium starts and installs the same inherited Linux Landlock TCP-connect allow rule for that single port. Docker remains `--network none`; the MCP runtime attests its pinned bundle, browser/worker identity and guard mode. Four effectful steps each require a fresh model decision, separate manual approval and current lease:

1. `browser.staging.open`: open `/app`, then separately observe its one `Draft` link.
2. `browser.staging.follow`: click that fresh link to `/draft`, then separately observe the exact empty form.
3. `browser.staging.fill`: fill `Message` with exactly `Hello from the local agent.`, then separately read the field.
4. `browser.staging.submit`: click `Save draft` once; the server accepts one exact `POST /submit`, redirects only to `/receipt` (absolute same-origin `Location` in proxy mode), and the separate readback verifies the receipt and one submission.

The server accepts only exact local Host, `GET /app`, `GET /draft`, `GET /receipt` after submission, and one `POST /submit` with exact same-origin `Origin`, form content type, decimal Content-Length and URL-encoded body. It returns empty-body errors for other methods/routes/hosts/body variants and does not serve subresources or arbitrary redirects. The default mode retains a 16-connection limit; an explicitly pinned fixture port sends Chromium GET and POST through the same-port HTTP proxy and uses a separate 64-connection ceiling because Chromium's background proxy connections otherwise exhaust 16 before receipt readback. Both modes retain the 2048-successful-response-byte budget and per-connection idle timeout. This pinned local test mode is not site-profile admission or real-site egress. The worker and runtime reject non-staging effectful tools even before `/app` is opened; the initial fixed-form `browser.observe` is read-only. The worker compares exact origin/route/DOM, allowed links/forms/inputs/buttons and readback state; stale symbolic references fail closed without blind action replay. Each observed local target also gets an opaque per-snapshot DOM-node marker; if the fixture re-renders an otherwise identical target, disables a control, reports busy/loading, or opens a dialog before an approved action, the worker returns `UI_CHANGED` before an MCP click/fill and consumes that snapshot so the old reference cannot be retried. These are synthetic-fixture freshness checks, **not** trustworthy identity or readiness proofs for an untrusted real website; a change between the separate check and click remains a race and cannot authorize a real-site write. The explicit migration `0010_staging_workflow.sql` only widens `desktop_tasks.kind`; existing v9 records and approvals remain intact.

This tests a reusable **bounded pattern**—request admission, finite staged action choices, fresh element references, one effectful POST and independent outcome—on fixed synthetic content. It does **not** provide browser-wide egress interception, DNS/TLS/account/tenant checks, arbitrary same-origin path policy, real user credentials, upload/download, or authority for an external URL. By default no profile is bound; an explicit [synthetic staging pin](LOCAL_STAGING_ADMISSION.md) can bind only this local fixture's exact origin/port and owned runtime. No real-site account or data-rights decision exists. A real target app still needs exact user-supplied URL, authorized test account/tenant, task/success oracle, request/redirect/resource policy and collection rights before W1–W6 acceptance can proceed.

## Verification

Unit tests cover additive v9→v10 migration, task/policy/typed value rejection, pinned opt-in admission, exact HTTP method/path/Host/Origin/body/redirect handling, one submission, same-semantics DOM-node replacement and disabled/busy/dialog refusal before submit. Explicit opt-in tests run the task on a fresh owned Ubuntu/Chromium/MCP runtime with a fixture decision engine or pinned real Decider. Both require four separate approvals and four independently matching verifications; stale symbolic reference has a separate no-POST integration test. Real Decider results are reported separately in `STATUS.md`. The first real-model wording attempt safely selected `ask_human` before any action; only explanatory option/goal wording changed before the successful rerun. Threshold, deployment pins and tool authority did not change. These are synthetic results, not real-site acceptance.
