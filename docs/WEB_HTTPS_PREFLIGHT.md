# Explicit host HTTPS entry preflight

`aos.web_https_preflight` is an opt-in host-side reachability check for a **stored**, immutable staging/production web-application profile. It requires the profile's exact SHA-256 twice, then resolves its entry hostname, rejects any non-global or unsupported DNS answer, connects to a selected public IP, and verifies the original hostname through normal TLS certificate validation. It sends one `GET` for the exact profile entry path. Only a non-redirected `200 text/html` response of at most 65,536 bytes succeeds. The response is hashed in memory and is not persisted or printed. The 1.3 report contains hashes, byte count, static HTML signal counts and explicit false authority flags; the synthetic example is not a real-site result.

The same in-memory first response is parsed only for counts of `<form>`, explicitly declared POST forms, cross-origin/unclassified form actions, `<script>`, stylesheet `<link>`, `<img>`, password `<input>`, cross-origin/unclassified `src` or `href` references on those resource tags, and `<meta http-equiv="refresh">` declarations. The latter count includes missing or malformed `content`; only a conservative numeric-delay `;url=` value is scope-classified. Cross-origin and unclassified refresh counts are separate, and neither navigates. Reference scope compares normalized scheme, hostname and effective port rather than raw spelling; empty/control-character/backslash references, credential-bearing or malformed/non-ASCII authorities and invalid ports are unclassified. A present `<base href>` makes relative form actions, resource references **and refresh URLs** unclassified rather than assuming entry-origin scope. No names, attribute values, URLs, HTML, cookies or credentials enter the report. Non-UTF-8 HTML yields `entry_html_signals=null` rather than guessed counts. These are static-source hints for onboarding, not proof of a supported form or application: invalid/implicit form methods, browser-specific refresh parsing, `srcset`, CSS imports, iframe content, dynamic JavaScript/fetch, login state, subrequests and browser-rendered DOM are not inspected. A count never authorizes any additional URL or tool action.

After registering a profile and independently confirming its allowed target, run:

```sh
PYTHONPATH=src .venv/bin/python -m aos.web_https_preflight \
  --profiles data/web-applications \
  --profile-sha256 <exact-sha256> --confirm-sha256 <exact-sha256>
```

This command **does make one external HTTPS request** when the profile names a reachable public site. Use it only for a target you are authorized to contact. The profile hash confirmation is an explicit CLI gate, not execution, collection, authentication, data-rights, or browser authorization. It does not submit credentials, follow redirects, load subresources, inspect the rendered page, or start Chromium. The existing owned browser remains `--network none`; no task scheduler, MCP or request interceptor is wired to this command. No target profile or real remote request was used in the project tests.

The authenticated Web Applications panel also offers an explicit **single entry check** for a registered staging/production profile. The operator selects its hash, types the exact stored entry URL, separately confirms the hash, and checks an initially-off authorization statement before pressing the button. `POST /api/web-applications/preflight` rejects extra/query/duplicate fields, mismatched profile/URL/confirmation and local-test profiles before network. Syntax and source/scope failures return `400` or `422` with no site request; a concurrent call returns `429` without starting a second probe. It uses the same bounded host probe, admits only one attempted GET per profile per console process, and allows only one concurrent probe; even a failed or cancelled network attempt consumes that in-process slot and may return `409`. The API and UI return only the contentless report with static counts, not HTML or credentials. The UI accepts legacy 1.0 transport-only, 1.1 resource-count and 1.2 form-action reports; it validates the added 1.3 refresh counts and rejects malformed reports. This is a user-triggered preflight, **not** browser navigation, task execution, account/site-outcome verification, collection permission or a durable site grant. Restarting the server resets the in-memory one-attempt guard, so the operator must still authorize every later attempt. An older running backend can serve newer UI assets without this API; its `404` is shown as unsupported and makes no site request. The API was tested against owned synthetic TLS with injected trust and patched public DNS; the UI completion test uses a clearly synthetic intercepted response. Neither is an external-site result.

For a stricter **task-bound preflight**, add a canonical bare `WebTaskAdmissionDraft` JSON file produced from the selected stored profile, task contract and declared runtime pin, plus its exact binding hash:

```sh
PYTHONPATH=src .venv/bin/python -m aos.web_https_preflight \
  --profiles data/web-applications \
  --profile-sha256 <exact-profile-sha256> --confirm-sha256 <exact-profile-sha256> \
  --binding-file /path/to/private/bare-draft.json \
  --confirm-binding-sha256 <exact-binding-sha256>
```

Before DNS or socket access, this path reopens the immutable profile chain, revalidates the draft's task/runtime/binding hashes, requires the selected profile and `browser.navigate` in the task tools, and checks the second exact confirmation. Its separate report includes the task, declared runtime and binding hashes plus the same first-response static counts without a second GET. `task_binding_verified=true` means only the **draft's structural profile/task/runtime binding** was rechecked. The declared runtime is **not observed** or connected: `runtime_identity_verified`, `browser_connected`, `execution_authorized`, `collection_authorized` and `training_ready` remain false. The synthetic fixture and local TLS test are not a real site or real runtime result. A bare draft must be prepared without credentials; the example `examples/web_application_binding.json` is a fixture wrapper, not a CLI input.

The socket connection is pinned to one resolved IP and TLS still authenticates the hostname. DNS and TLS/HTTP errors fail closed. One absolute network-phase deadline bounds the caller's DNS wait, connection, TLS, request, HTTP header parsing and bounded body reads; a header that drips bytes cannot extend it by resetting a per-read socket timeout. Only one DNS resolver call may be active: if resolution exceeds the deadline, no HTTP connection starts, but the daemon resolver thread can remain inside the system resolver until that call returns. A later probe waits for that one slot only within its own deadline. Profile validation and local TLS-context setup occur before the network-phase deadline; use an external process timeout when a strict whole-CLI lifetime or resolver cancellation is required. A successful report demonstrates only that one HTML entry response was reachable at that instant. It does not establish account/tenant access, site semantics, redirect or subresource policy, continued DNS safety, task budget enforcement, or W1–W6 acceptance.

Validation uses a temporary local TLS server, synthetic certificate and a patched public DNS answer; it never contacts the synthetic `.invalid` example or any external domain: `PYTHONPATH=src:tests .venv/bin/python -m unittest tests.test_web_https_preflight -v`. Canonical report contracts are `schemas/web_https_preflight.schema.json` and `schemas/web_bound_https_preflight.schema.json`.
