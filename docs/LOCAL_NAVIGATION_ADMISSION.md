# W1 synthetic navigation profile/runtime gate

Guarded MCP browser pages also install an exact method+URL Playwright request route before navigation. The runtime handshake and every profile-bound gateway recheck require its installation flag. This browser-level layer rejects an off-route request before the fixture server, but is not a standalone network boundary; network-none Docker, inherited Landlock TCP guard, proxy shape and server-side checks remain mandatory. It does not enable real-site HTTPS access.

`aos.local_navigation_admission` adds an **opt-in additional check** for the existing fixed, networkless `browser_local_navigation` task. A caller explicitly supplies a registered immutable `local_test` profile and a `SyntheticNavigationPin` to `DesktopScheduler(local_navigation_profiles=..., local_navigation_pin=...)`. Neither argument is supplied by the normal launcher or UI, so the default scheduler path is unchanged.

The selected profile must declare exactly `http://127.0.0.1:<fixture_port>/start`, one matching local origin, and the `synthetic-local-navigation` task key. `fixture_port` is an explicit nonprivileged pin (1024–65535); a port already in use fails rather than silently selecting another. Before creating a job, the scheduler checks that profile and the selected parent desktop/container/image, MCP bundle, worker, fixture and runtime-pins hashes against the currently owned, network-none Docker desktop. After the MCP worker starts, it requires the Landlock-attested port to equal the pin and binds the observed child browser runtime ID in memory. It reopens the profile and rechecks Docker ownership, running worker, pinned identities and isolation before each gateway observation/action, including independent readback. Pause/resume keeps the same child ID; stale ownership or changed identity fails before another tool call. Existing lease and separate per-action user approvals remain mandatory; `approve_all` stays forbidden for this task.

In this opt-in mode, the worker binds the pinned `127.0.0.1` fixture port before launching Chromium and installs a Linux Landlock TCP-connect rule allowing only that port for its inherited process tree. It probes both the allowed fixture and a denied port before attesting the guard in the runtime handshake. The pinned MCP browser is configured to proxy HTTP through that same local port; the fixture server then accepts only absolute-form requests at the exact profiled origin and exact `GET /start` or `GET /details`. Direct origin-form requests, other methods/routes/Host/body encodings and off-origin absolute URLs are rejected. A successful page result therefore requires the proxy-shaped request path, not merely a configured MCP flag. The server caps one pinned proxy runtime at 64 connections (16 without proxy) and 2048 successful response-body bytes. A 1-second per-connection socket idle timeout closes an incomplete request instead of leaving the single-threaded server indefinitely occupied; it is not an absolute request deadline or complete slowloris defense. If guard installation or attestation fails, the worker cannot start and fixture tools are rejected. The normal fixed-form MCP mode does not install this guard; an unpinned fixture task still chooses a dynamic port and does not use this proxy. Docker `--network none` still prevents external networking. This proves only an exact local **HTTP fixture** request path, **not** general HTTPS CONNECT/redirect/resource enforcement, UDP, DNS/IP rebinding, account/tenant isolation or real-site egress. The opt-in check reports `profile_to_origin_bound=true` for this fixture only, while `account_role_verified=false`, `execution_authorized=false` and `collection_authorized=false` remain. This is not real-site admission, a new collection grant or a reusable execution lease. Model policy, lease, approvals and independent outcome verifier still define the only executable scope. Migration `0011_desktop_web_profile_bindings.sql` records an append-only job/run/profile/pin/browser-runtime metadata link only for an explicitly pinned run. It does not add remote proxy/egress or site skill execution.

`schemas/synthetic_navigation_pin.schema.json` is the canonical input contract and `examples/synthetic_navigation_pin.json` is explicitly synthetic. Constructing a real pin requires explicit selection of the live parent runtime and current package/worker hashes; copying the example pin cannot match a real process. Focused tests: `.venv/bin/python -W error::ResourceWarning -m unittest discover -s tests -p test_local_navigation_admission.py -v`. Real-site W1 still needs a target app, exact request/redirect/origin enforcement, account and tenant evidence, authorized task verifier and data rights; this fixture gate cannot substitute for them.

The separate opt-in integration test `test_desktop_mcp.MCPSchedulerIntegrationTests.test_opt_in_synthetic_profile_pin_rechecks_real_owned_runtime` uses a fresh owned Ubuntu/XFCE/Chromium/MCP runtime, a private synthetic profile and a pin computed from that exact runtime. It exercises two independent approvals and two independent verifications, including exact profile URL ↔ bound fixture port attestation; it does not visit an external site. Enable with `PYTHONPATH=tests:src AOS_DESKTOP_TESTS=1 AOS_DESKTOP_MCP_TESTS=1 .venv/bin/python -m unittest test_desktop_mcp.MCPSchedulerIntegrationTests.test_opt_in_synthetic_profile_pin_rechecks_real_owned_runtime -v` after preparing the pinned Docker/MCP runtime.
