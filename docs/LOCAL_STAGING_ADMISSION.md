# W1 synthetic staging profile/runtime admission

The guarded MCP page now installs an exact GET/POST URL route before navigation. Its installation flag is rechecked with the pinned local profile/runtime identity; off-route browser requests abort before the fixture server. The network-none container, Landlock port rule, same-port proxy and exact server GET/POST rules remain the actual layered fixture boundary. This does not authorize remote HTTPS, account actions or collection.

`SyntheticStagingPin` adds an optional, in-memory identity gate to the fixed, networkless `browser_staging_workflow`. It requires one immutable `local_test` profile with exactly `http://127.0.0.1:<fixture_port>/app`, one matching allowed origin, and the `synthetic-staging-workflow` task key. A caller supplies the selected `WebApplicationProfiles` store and a pin computed from the **currently owned** Docker desktop, prepared MCP bundle, worker, fixture and runtime hashes to `DesktopScheduler(local_staging_profiles=..., local_staging_pin=...)`. Supplying one without the other, a different explicit staging port, or no staging MCP manifest fails before a task starts. The normal launcher and UI do not supply this pin; `--staging-fixture-port` alone is only a developer-mode port selection, not a profile admission.

Before inserting a job, the scheduler reopens the profile and checks the live parent desktop identity, pinned bundle/worker/fixture hashes and exact fixture port. The staging worker binds that port before Chromium starts, installs the inherited Landlock TCP-connect rule and enables its same-port HTTP proxy. After startup and before every gateway observation/action, the scheduler rechecks the profile, owned desktop, child runtime ID, container/image, network-none status, pinned hashes, guard attestation, proxy and staging modes. A paused task must resume on the same child runtime identity. Stale or changed profile/runtime evidence fails before another MCP action; lease, policy, four separate approvals and independent verification still apply.

At run creation, migration `0011_desktop_web_profile_bindings.sql` records the exact selected profile hash, task key, canonical pin/hash and observed child browser runtime ID against one job/run in the private trajectory DB. The insert follows a fresh live binding check in the same transaction as the job's run-ID update. The row is append-only, and job kind/run/runtime IDs cannot change afterward; failed runs retain their binding. Earlier runs are not backfilled. This is provenance metadata, not a grant, and only exists when this opt-in pin is supplied.

This pin **does not** authenticate a tenant/account, approve an effectful action, grant learning collection, establish data rights or permit remote networking. The status `synthetic_runtime_match_only` and `profile_to_origin_bound=true` refer only to this local fixture; `execution_authorized`, `collection_authorized` and `account_role_verified` remain false in the pin report. The actual fixed task's separate policy and manual approvals still authorize its one synthetic POST. It is not a generic request interceptor or W1 real-site acceptance. HTTPS/redirect/subresource/DNS/IP, account/tenant, task oracle and reviewed data scope remain open.

`schemas/synthetic_staging_pin.schema.json` is canonical. `examples/synthetic_staging_pin.json` is explicitly synthetic and cannot match a live runtime without replacing every selected identity and exact profile port. Keep private profile files and local trajectory data out of the source package.
