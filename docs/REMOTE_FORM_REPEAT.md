# W6 exact HTTPS form repeat measurements

`python -m aos.remote_form_repeat --database <private trajectory.sqlite> --profiles <private profile store> --selected-profile-sha256 <sha256> --selected-plan-sha256 <sha256>` reads one frozen SQLite audit snapshot and emits a contentless canonical JSON report. For six-approval state forms, add `--selected-state-plan-sha256 <exact state hash>`. It makes no browser, model, training, or network call.

An authenticated `GET /api/remote-form/repeats` uses only the current backend's pinned profile, exact form plan, optional exact state plan and trajectory DB; it accepts no caller selection or query string. The endpoint rejects Cookie plans, cross-store pins, concurrent inspections and changed/incomplete evidence. It returns 404 when no form plan is pinned, 409 when evidence is unavailable, and 429 for a concurrent inspection. Development reads it on opening, explicit refresh and latest-job status changes; it displays only aggregate counts and durations, never the report hashes. Older backends' 404 is not treated as a zero-success measurement. The browser request does not start a task or authorize data collection.

The denominator is **every terminal, post-admission `desktop_remote_form_bindings` row in that database** with the exact selected profile and form plan hashes **and selected mode**: no state binding for basic, or the exact state-plan hash for six-approval mode. It is not a caller-picked list of successful run IDs; basic and state attempts cannot be silently mixed. It requires 2–32 bound attempts, matching stored real-model flags, canonical draft/plan and state binding, no Cookie binding, unchanged deployment snapshot, and matching terminal job/run status. Each successful row must separately pass its four- or six-approval, one-POST source audit **inside the same frozen SQLite snapshot** as the denominator; it no longer copies the database once per successful run. In state mode this includes separate declared before/after readback verification, not semantic application outcome. A malformed successful row fails the whole report; it is never silently excluded. Failed and cancelled rows remain in the denominator. Pre-admission attempts without an immutable binding are outside this report, so it is not an all-started-job success rate.

Elapsed p50/p95 uses nearest-rank percentiles over terminal job `created_at`→`updated_at` wall time, **including approval windows**. First-action p50/p95 uses only rows with a recorded `browser.form.open` action and reports that sample count separately; this is the first persisted action intent timestamp, **not** a measured first visible browser effect. Model call count includes all statuses and both roles, up to 256 calls per run; latency sum includes only non-null finite measurements, with its own sample count so missing timeout/error timings are visible. These are recorded durations, not controlled resource isolation measurements. The `real_model` bit and deployment snapshot are database claims, not independent model artifact attestation.

Report schema **1.2** retains the 1.1 terminal approval-window count and recorded `created_at`→`updated_at` sum. Each window must be inside its job and non-overlapping; pending or approved-but-unclosed windows, excess stages, and changed timestamps fail the entire report. Per-attempt elapsed time minus its approval-window sum is reported as a separate nearest-rank p50/p95. This is **not** pure model or browser execution time: it still combines model preparation/inference, scheduler, browser and network costs. The approval window includes both manual and delegated approvals and some validation/consumption overhead; it is not a precise human reaction-time measurement.

For each **transport-verified** run, schema 1.2 also measures each approved stage from its durable `consumed` timestamp to the matching action's `completed_at`. It reports per-stage sample count and nearest-rank p50/p95 for four basic stages or six state-plan stages; if no run passes transport audit, the stage map is empty. The same snapshot must contain exact action/approval IDs, terminal success and ordered timestamps. Missing or reversed timestamps fail closed; failed/cancelled runs still count in the overall denominator but do not enter these stage samples. This interval includes scheduler/policy/gateway and browser or host-network work; it does not isolate a pure browser or network duration, and the intervals do not sum to total task time. The Development panel accepts older 1.1 summaries without stage cards and rejects malformed 1.2 stage metrics; 1.0 remains unavailable rather than displaying missing numbers as zero or `NaN`.

The report establishes only bounded transport-level repetition. It does **not** verify account, data rights, application-specific outcome, cross-session generalization, improvement versus base, or W1–W6 acceptance. Static Cookie and other form variants remain excluded. The report and database are private; even SHA-256 metadata can identify a low-entropy plan. Basic and state modes have separate canonical contracts and explicitly synthetic examples: `schemas/remote_form_repeat.schema.json`, `examples/remote_form_repeat.json`, `schemas/remote_form_state_repeat.schema.json`, and `examples/remote_form_state_repeat.json`.
