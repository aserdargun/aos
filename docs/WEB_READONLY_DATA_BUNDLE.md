# W1 exact read-only JSON managed bundle

The v2 `WebReadOnlyDataBundlePlan` is a separate contract; existing queryless v1 static plans and their hashes are unchanged. It binds one registered staging/production profile and task to 1–8 exact same-origin JS/CSS/images URLs and 1–4 exact same-origin `application/json` GET URLs. The entry URL remains queryless. Static asset and JSON URLs may each have a fixed canonical query of 1–8 unique `key=value` pairs (up to 512 URL-encoded ASCII characters; printable ASCII values up to 128 characters each). This is for non-secret static filters only: query URLs appear in private plans and operator UI, and the validator cannot detect tokens, personal data, or other secrets. Do not put them in a query. The plan grants neither execution nor collection authority.

The host fetch checks the exact plan SHA-256 and resource index before DNS or TLS. It uses public-IP DNS, selected-IP TLS hostname verification, one redirectless `200`, exact MIME, identity encoding, and a 256 KiB JSON response bound. No Cookie, Authorization, POST, client-supplied headers, or automatic retry is available. Raw response bytes stay in the private process/browser transport; reports retain only hashes and sizes.

`ExactStaticBundleRelay` also accepts this v2 plan in its direct runtime path. Only after `arm()` does the private one-use socket serve entry HTML, each static asset, and each JSON resource once. The pinned Ubuntu Chromium/Playwright MCP worker blocks off-plan document/subresource/fetch/XHR requests before the socket; JSON GET requires the main frame and exact resource URL/index, including its query. CSP restricts connections to planned JSON origin/path sources; CSP does not enforce query equality, so the exact browser gate and relay do. The browser container remains network-isolated. The relay report binds entry, static and JSON response hashes without claiming browser identity, user authorization, site outcome, or training readiness.

**Managed opt-in:** `plan-remote-readonly-data` accepts an owner-only `data/` JSON source with exactly `assets` and `data_resources`, then writes a new canonical owner-only v2 plan without network access. `preview-remote-readonly-data` revalidates that private plan. Alternatively, authenticated Web applications takes 1–8 exact JS/CSS/images entries and 1–4 exact JSON GET URLs for a registered single-page task, previews the non-authorizing plan hash without network/file writes, then requires that exact hash to register an immutable `0600` plan under `data/web-readonly-data-drafts/`. The panel shows offline preview and safe new-start commands but does not execute them. A safe new `start --remote-readonly-data-plan-file` copies and SHA-256 pins either private plan with the exact registered profile and task. V1 and v2 plan flags are mutually exclusive; neither changes an already running session. The existing internal `browser_remote_static_assets` task kind selects the pinned v2 mode, but the Tasks panel labels its JSON scope and exact URLs separately. `approve_all` is disabled. One persistent manual approval binds entry, all JS/CSS/images, all JSON GETs, and the plan hash before any host GET or MCP worker starts; rejection produces no host request. The scheduler writes append-only job/run/plan/runtime and independent content-free readback verification, including separate JSON response hashes. `arm()` alone is never human approval.

Example, after registering the exact profile and task under `data/`:

```sh
./scripts/aos-v1 plan-remote-readonly-data --remote-entry-profile-sha256 PROFILE_SHA256 --remote-entry-task-file data/task.json --remote-readonly-data-source-file data/readonly-source.json --remote-readonly-data-plan-file data/readonly-plan.json
./scripts/aos-v1 preview-remote-readonly-data --remote-entry-profile-sha256 PROFILE_SHA256 --remote-entry-task-file data/task.json --remote-readonly-data-plan-file data/readonly-plan.json
./scripts/aos-v1 start --remote-entry-profile-sha256 PROFILE_SHA256 --remote-entry-task-file data/task.json --remote-readonly-data-plan-file data/readonly-plan.json
```

The source shape is `{"assets":[{"url":"https://example.invalid/assets/app.js","content_type":"application/javascript"}],"data_resources":[{"url":"https://example.invalid/api/summary?view=compact&page=1"}]}`. These values are illustrative only; no real account or site grant is bundled. V1 `browser_remote_static_assets` still denies all XHR/fetch. V2 has a [separate read-only W4 source audit](REMOTE_READONLY_DATA_SOURCE.md) and an [explicit consent-bound metadata-only stream](REMOTE_READONLY_DATA_STREAM.md), but no independent account/right verification, real-site outcome oracle, reviewed dataset or training readiness. A real target URL, account, allowed task, and data rights are still required before W1 acceptance; W1–W6 remain open.

Validation uses a synthetic local TLS server with patched public DNS and the owned `--network none` Ubuntu Chromium/Playwright MCP fixture. It checks wrong plan/index, MIME/size, pre-arm/replay, wrong-method exact URL, off-plan fetch, DOM update from JSON, response hashes, v1 regression, managed approval/job/run, private manager pin and EN/TR Tasks UI. Add `AOS_READONLY_DATA_REAL_DECIDER_TESTS=1` to the managed scheduler test to use the actual pinned Decider rather than the fixture engine. The synthetic fixture and canonical schemas are `examples/web_readonly_data_bundle.json` and `schemas/web_readonly_data_*.schema.json`.
